# DOPIS-LEARNING-010 — Validator vocabulary alignment

- Observation: independent review found that `scripts/validate_specification.py` built `dependency_rationale.*.source_refs` acceptance from requirement, use-case, story, and acceptance-criterion ids plus technical-baseline decision ids (`TB-*`), while `DOPIS_VERTICAL_SLICE_TRACEABILITY_CONTRACT.json` limits that field to requirement, use-case, story, or acceptance-criterion ids only.
- Impact: the validator could accept a dependency-rationale source the contract explicitly does not permit, because a `TB-*` id happens to resolve elsewhere in the repository; a contract reader would have no way to know the implementation was actually more permissive than the declared vocabulary.
- Cause: `source_reference_ids` was assembled from every id set already in scope at the call site for convenience, rather than the exact set the contract names for that field.
- Containment: preserved the full reviewed 18-slice model, its 4 hard dependency edges (2 induced, 2 additional source-backed) and their existing rationale content, all coverage/order checks, and `NOT_GRANTED`/`NOT_STARTED` authority states; changed no requirement, story, use case, acceptance criterion, minimum technical baseline, or application code.
- Correction: removed technical-baseline ids from the `source_reference_ids` union so the validator accepts only requirement, use-case, story, or acceptance-criterion ids for `dependency_rationale.*.source_refs`, matching the contract exactly; added a focused negative fixture citing a real, resolvable `TB-*` id in that field to prove it is still rejected, alongside the existing positive/control fixture for a valid justified additional dependency; aligned the `VERTICAL_SLICE DEPENDS_ON VERTICAL_SLICE` `checked` description in the traceability matrix to state the source-vocabulary limit.
- Prevention: a validator's accepted-reference vocabulary for a contract-defined field must be built from exactly the id sets the contract names for that field, not from whatever sets happen to be in scope; a resolvable id from another namespace must not be accepted merely because it exists in the repository.
- Evidence limits: this record corrects validator source-vocabulary enforcement and one matrix description only; it reopens no product/operational judgment and grants no implementation, ADR, test, task, or execution-packet authority.
- Validation plan: run the locked GOV-GEN consumer validator, `scripts/validate_specification.py`, `scripts/test_validate_specification.py`, and confirm the new negative fixture rejects a resolvable `TB-*` source_refs entry, the existing positive/control fixture still passes, and `git diff --check`.
